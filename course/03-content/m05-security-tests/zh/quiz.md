# 测验 M5 — 规格驱动的 SaaS：多租户安全与验收
> AI Product Studio（APS-3）的一部分 · 8 道题（6 道选择题 + 2 道简答题）· 附答案

**Q1.** `AGENTS.md` 写道：「缺少 `org_id` 过滤就是跨租户数据泄露。把它当作 P0 缺陷处理。」为什么是 P0，而不是一个普通缺陷？

A. 没有 `org_id` 索引时，它会拖慢查询。
B. 一条未过滤的查询就可能把另一个租户的数据行返回给一个合法的、已认证的用户——这是多租户 SaaS 最严重的失败，对应最高的严重级别。
C. 它只在管理员路由上才要紧；志愿者路由是只读的，因此是安全的。
D. 一旦模型声明了 `org_id`，SQLAlchemy 就会自动加上租户过滤。

**Q2.** 一个教会的敬拜协调人需要带领礼拜，但不应该管理这个组织。SignUpFlow 会授予什么？

A. 一个按部门划分的 `worship_manager` 权限角色。
B. `admin`，因为他们带领一个事工——资格意味着信任。
C. 访问角色 `volunteer` 加上排班资格 `worship_leader`——资格从不赋予权限。
D. 两个权限角色 `volunteer` 和 `admin`，规范化后放进同一个数组。

**Q3.** 一个已登录的成员请求了一个存在于另一个租户中的人员 id。什么样的响应能防止资源枚举？为什么？

A. `403`——请求者必须得知资源存在，但不属于他们。
B. `404`——这个 id 在操作者的租户内查找，因此他人的资源和不存在的资源无法区分。
C. `401`——必须针对每个目标资源重新验证令牌。
D. 处处都用 `403` 比混用状态码更安全；攻击者无法从单个状态码中获知任何信息。

**Q4.** `tests/unit/test_api_route_auth_policy.py` 实际比较的是什么？

A. OpenAPI 快照与生成的移动端客户端。
B. `api/route_auth_policy.py` 中的策略字典与实时路由表——在路由缺失、过期或错接时失败（例如策略写的是 `admin`，路由却接上了 `get_current_user`）。
C. README 中的路由列表与 `CLAUDE.md` 中的路由列表。
D. 每个路由的文档字符串与它声明的依赖。

**Q5.** 你的产品会起草发给志愿者的通知，由一个模型来写。你担心的失败是：通知里点名了一位不在排班表上的志愿者。哪个层级能观察到这种失败？一次通过的结果允许你说什么？

A. 集成层级，对照一个夹具断言通知字符串；运行通过就意味着通知是正确的。
B. 第八个层级——在一组已知正确答案的固定输入上、走真实提示词路径的行为评测——一次通过的运行只允许你说「这个模型在这些输入上、在这个日期表现如此」；七个确定性的层级观察不到它，因为输出每次运行都不同。
C. 契约层级，因为通知是 API 表面的一部分。
D. 没有任何层级能观察到；模型输出本质上无法测试，所以它永远属于人工层级。

**Q6.** 浏览器运营手册会亲自检查每一份已发布的排班表，而不是信任求解器的指标。独立判定器验证什么？为什么健康分 100 还不够？

A. 它验证求解器运行过；健康分 100 表示没有任何软约束惩罚，所以已经足够。
B. 它验证角色人数精确、指派人员各不相同且合格、不重叠和负载均衡——从排班表重新计算，因为健康分是求解器自己的输出（有任何硬约束违规时为 0，否则为 100 − soft/10），而自我报告的分数不是判定器。
C. 它验证在 360px 和 1440px 下的页面加载时间。
D. 它只验证关键角色，因为其他角色都是软约束。

**Q7.** 在 `docs/playbooks/coverage.json` 中，状态为 `blocked` 的场景意味着什么？校验器为什么要求这类行必须包含 `manual` 层级？为什么「blocked」比悄悄删掉这一行更好？

**Q8.** 为以下要求写出测试断言序列：「志愿者 A 不能编辑志愿者 B 的可用时间，并且 B 的记录没有改变。」按顺序写出每一条断言、你预期的状态码，以及大多数团队会忘掉的那一条断言。

---

## Answer key

**Q1 — B.** 这个过滤就是租户边界；漏掉它，就会把跨租户数据暴露给一个完全合法的会话——之所以是 P0，是因为它属于数据泄露这一类，而不是性能或风格问题。*（目标：M5.1 — `AGENTS.md`，“Multi-tenancy and auth”。）*

**Q2 — C.** 恰好一个权限角色（`volunteer`|`admin`），资格放在同一个数组中，但从不被当作权限：「不要仅仅因为某人带领一个事工就授予管理员权限」（`docs/playbooks/church.md`）；`normalize_roles` 会拒绝第二个权限角色（"Select exactly one account access role"，`api/roles.py`）。*（目标：M5.2。）*

**Q3 — B.** 「猜测的资源标识符在操作者的租户内查找，无论它属于他人还是不存在，都返回 `404`」（`docs/API_AUTHORIZATION.md`）；`get_person_in_actor_org` 实现了这种查找（`api/dependencies.py`）。A 和 D 是关于枚举的误解——统一返回 403 反而会确认资源存在。*（目标：M5.1。）*

**Q4 — B.** `ROUTE_AUTH_POLICY` 与实时路由之间的集合相等比较抓住缺失/过期；依赖树遍历抓住错接——这就是 `tests/unit/test_api_route_auth_policy.py` 针对 `api/route_auth_policy.py` 的机制。*（目标：M5.2。）*

**Q5 — B.** `docs/TESTING.md` 中的七个层级都是对确定性输出做断言——单元层级基于模拟鉴权，API/安全层级在隔离的 SQLite 上使用真实 JWT，集成层级基于真实数据库（模拟它是 `AGENTS.md` 中被点名的反模式），浏览器层级用 Playwright 测试可丢弃的实时应用，契约层级基于 OpenAPI 快照。一份起草的通知每次运行都不同，却仍然必须正确，所以能观察到它的层级是行为评测。（A）把夹具误当成了判定器：一个预期字符串只测到一种措辞，而不是行为。（D）是绝望之下的建议，而清单有更好的答案——`mini-flow` 的 MF-05 正是以 `blocked` 状态、带 `manual` 层级承载这个场景，直到评测套件出现为止（`course/03-content/m05-security-tests/mini-flow/tests/playbooks/coverage.json`）。一次通过的评测给你的许可，是一个带分母和日期的测量结果，与 M6 中主张层级的含义相同：永远不是「这个助手是准确的」。*（目标：M5.3 — `docs/TESTING.md`；评测层级见 M3.2 分段。）*

**Q6 — B.** 判定器「在两种浏览器宽度下、于发布之前」检查角色人数、指派人员各不相同且合格、不重叠以及负载均衡（`docs/playbooks/README.md`）；有任何硬约束违规时健康分 = 0.0，否则为 `max(0.0, 100.0 - soft_score/10)`（`api/core/solver/heuristics.py`）——求解器不能给自己的作业打分。*（目标：M5.3。）*

**Q7 — Acceptable answer:** `blocked` 表示一个目前无法运行的必需场景——是剩余工作，「而不是已通过的场景」（`docs/playbooks/church.md`）；校验器强制 `manual`/`blocked` 行带上 `manual` 层级，使它们无法冒充 automated（`tests/playbooks/coverage.py`）。删除这一行更糟：必需的 id 是固定的（BO-01..12；CH-01..08），所以移除会让收集在任何测试运行之前失败——清单让范围保持诚实，而不是让它缩水。一个 `blocked` 行是诚实的证据；一行消失则是一个无声的覆盖谎言。*（目标：M5.3 — `tests/playbooks/coverage.py`、`tests/playbooks/plugin.py`。）*

**Q8 — Acceptable sequence:** （1）用真实 JWT 以 A 的身份认证；（2）在尝试之前给 B 的可用时间行拍快照（或记录其哈希）；（3）以 A 的身份尝试编辑；（4）断言被拒绝——同租户的同事得到 403，若 B 属于他人或不存在则得到 404（在 A 的租户内查找）；（5）重新读取 B 的记录，断言它逐字节未变。被遗忘的断言是（5）——「断言被禁止的写入不改变数据库状态」是 SignUpFlow 变更协议的第 4 步（`docs/API_AUTHORIZATION.md`）；BO-03 的浏览器演练「在前后比较两条记录，以证明这次拒绝没有改动目标成员」（`docs/playbooks/README.md`）。*（目标：M5.1/M5.2。）*
