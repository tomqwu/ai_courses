## M0.1 — 三种产品原型，一套方法

<!-- _diagram: grid -->

- 类型 1 — 端侧原生 AI 应用
- 类型 2 — 规格驱动的 AI SaaS
- 类型 3 — 专业知识内容产品

- 技术重心各不相同
- 背后是同一套方法
- 你只学一次方法，却学到三遍

<!-- NOTES: 一个独立技术构建者能交付的东西，几乎都落在这三种形态之一。类型 1 运行在用户的设备上，卖的是隐私和速度。类型 2 运行在服务器上，卖的是可靠性和多用户信任。类型 3 卖的是经过验证的知识——一件研究产物，而不是软件。它们需要的技术技能几乎没有重叠。方法却是重叠的，而这种重复正是本课程在教学上的全部押注。时间安排：3 分钟。过渡：来认识类型 1，ListenToMe。 -->

- 每项资产都是一个文件，带日期或可由机器检查
- 没有一项是用户推荐语

<!-- NOTES: 这就是本课程赖以运转的定义：生产级意味着一件已交付的产物，附带你能打开并验证的证明。一个由覆盖率运行生成的徽章，一行带日期的证据，一份逐项附有验收标准的公开审计。三者都是文件。用户推荐语、README 里一句「已完成」的说法，或者仅仅是仓库存在，都不是证据。你的实验会按照同一条标准评分，这就是为什么每个实验都以一件产物结束，而每件产物都以证据结束。时间安排：3 分钟。过渡：这三个产品共享一个可重复的循环。 -->

## M0.2 — 从规格到交付的循环

```figure
kind: flow
alt: 从规格到交付的循环——研究、规格、构建、验证、发布、证明——然后为下一次变更回到研究。
loop: yes
step: 研究 — 调研、竞品、定位 @ 研究阶段产出
step: 规格 — 智能体能执行的内容 @ 规格阶段产出

step: 验证 — 测试、覆盖率底线、运营手册 @ 验证阶段是测试
step: 发布 — 公证、版次、部署 @ 发布阶段是签名
step: 证明 (hl) — 证据、来源追溯、诚实的主张 @ 证明阶段是
```

<!-- NOTES: 六个阶段，你会在本课程的每个模块里把六个阶段全部走一遍。研究阶段产出的是一件定位产物，而不是一句口号。规格阶段产出的东西，能让一个全新的智能体会话在没有对话记忆的情况下执行。构建阶段先写测试。验证阶段是一份记录，而不是一种感觉。发布阶段是签名、编订版次、部署。证明阶段是对哪些已验证、哪些未验证的诚实交代。把这张图抄进你的笔记——你马上就会再次用到它。时间安排：5 分钟。过渡：每个阶段背后都有一件真实的产物。打开这些文件。 -->

## 证明是主干

- 测试验证你构建的东西
- 证据纪律验证你交付的东西
- SignUpFlow 的记录保留了它的失败

```text
The first full browser run had 32 passes and one recurring-delete timing
failure. The targeted rerun and repaired full rerun passed; this initial
failure is not omitted from the evidence.

| Full API mypy | Existing debt: 835 errors in 40 files; not a pass |
```

指针：`SignUpFlow/docs/playbooks/validation.md:45, 50-52`

<!-- NOTES: 读一读那份验证手册，你会看到工程师在列出自己的失败：一个让测试变得不稳定的浏览器时序竞争，以及一行明确写着 "not a pass" 的类型检查欠账。他本可以删掉这两行。保留它们，才让那些通过的数字可信。当你写结业项目的证据记录时，失败部分不是可选的——一份没有局限的记录读起来就是未经验证的，因为它通常确实如此。时间安排：4 分钟。过渡：现在由你来应用这套方法，就在接下来的十二分钟里。 -->

## 两种有效环境（说明你用的是哪一种）

kind: system
alt: 把你的实验环境看作一个系统：终端和 TinyCopilot 都与你机器上的 Ollama 守护进程通信；守护进程要么由本地模型作答，要么在模型名以 :cloud 结尾时把提示词转发给 Ollama Cloud。
