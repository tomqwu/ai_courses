# Deep-Read Report: SignUpFlow (The Spec-Driven AI SaaS)

> Source: subagent deep-read of the `SignUpFlow/` clone, a sibling of `course/` in the workspace root (all claims grounded in files read directly from the repo).

## 1. The Product and the Archetype Lesson

SignUpFlow (github.com/tomqwu/SignUpFlow, MIT) is a multi-tenant volunteer-scheduling SaaS for churches, sports leagues, and non-profits. Stack: FastAPI + SQLAlchemy 2.0 + Pydantic 2 (Python 3.11+), JWT auth (HS256, 24h expiry) + bcrypt, SQLite dev / PostgreSQL prod, an HTMX + Alpine.js + Jinja2 web app served by the same FastAPI process, a Flutter mobile app (`mobile/`), and a YAML-in/JSON-out CLI (`python -m api.cli.main init|solve`). The core is a greedy heuristic solver that generates fair rosters under constraints, reporting a health score, hard/soft violations, and fairness stdev.

The product itself is technically ordinary — CRUD + scheduling. What makes it sellable course material is the *process* wrapped around it: a complete governance system for building production software with AI agents. The repo demonstrates: a project constitution, per-agent rule files (AGENTS.md/CLAUDE.md/Copilot), a spec-kit artifact pipeline, a 7-tier test pyramid, playbook-based acceptance with a machine-readable coverage manifest, and a radical "no CI — all validation local, evidence recorded" policy. The archetype lesson: **AI agents don't replace process; they raise the stakes for it.** When code is generated at agent speed, the bottleneck moves to specification, verification, and honesty about what was actually validated. Note also the honest-scope posture: billing/SMS code is registered but 404-gated behind `BILLING_ENABLED=false`/`SMS_ENABLED=false`, and docs repeatedly state what is NOT proven (external delivery, PostgreSQL parity beyond allocation claims, deployment).

## 2. The Spec-Driven Methodology as Practiced

**Workflow** (docs/SPEC_KIT_SETUP.md): GitHub spec-kit slash commands in Claude Code: `/speckit.constitution` → `/speckit.specify` → `/speckit.clarify` (max 3 questions) → `/speckit.plan` → `/speckit.checklist` → `/speckit.tasks` → `/speckit.analyze` → `/speckit.implement`. Helper scripts in `.specify/scripts/bash/`; templates in `.specify/templates/`.

**Artifact anatomy** (observed across `specs/`):
- **spec.md** — WHAT, technology-agnostic: prioritized user stories (P1/P2/P3, each *independently testable* = an MVP slice per the template), Given/When/Then acceptance scenarios, edge cases, FR-xxx requirements, key entities, SC-xxx measurable success criteria, dependencies/assumptions, open decisions, changelog. The template mandates stories be independently implementable/testable/deployable/demonstrable, and allows `[NEEDS CLARIFICATION]` markers.
- **plan.md** — HOW: technical context (language, deps, storage, perf goals, constraints, scale), a **Constitution Check gate** ("Must pass before Phase 0 research. Re-check after Phase 1 design."), project structure with `[NEW]`/`[MODIFY]` annotations, and a Complexity Tracking table used only when constitution violations must be justified.
- **research.md** — Phase 0: numbered decisions with options evaluated (pros/cons), rationale, implementation sketches, cost, risk table. Spec 014's research.md makes 8 decisions (Redis for rate limits; TOTP over SMS — citing NIST deprecation of SMS and SIM-swap risk; PostgreSQL table for audit logs; itsdangerous for CSRF; bleach for sanitization; Redis sessions; FastAPI middleware for headers; itsdangerous reset tokens), each with rejected alternatives.
- **data-model.md** — Phase 1 (in specs 000/001/011/015/016/019; 014 deliberately omits it).
- **contracts/** — per-domain API contracts: config tables, class interfaces with docstrings/examples, middleware behavior, i18n error keys, Redis key schemas, storage estimates, monitoring metrics, unit/integration/E2E test sketches, performance benchmarks, tuning. 014 has 6 contracts (~4,700 lines).
- **quickstart.md** — timed deployment guide with prerequisites, steps, verification checklist, troubleshooting.
- **checklists/requirements.md** — spec-quality gate before planning (no implementation details leaked, requirements testable, no NEEDS CLARIFICATION left).
- **tasks.md** — Phase 2: checkbox tasks `[ID] [P?] [Story]` grouped Setup → Foundational (blocking) → one phase per user story (tests written first and failing, MVP checkpoint) → Polish; every task names an exact file path; dependency and parallel-execution sections.

**Tasks → implementation:** tasks cite exact paths. Implementation can run as a **Ralph loop** (constitution "Context A"): an agent picks the highest-priority incomplete spec, completes ALL acceptance criteria, outputs `<promise>DONE</promise>` (`scripts/ralph-loop.sh`). Sprint-completion specs (023, 024) record what shipped.

**Governance stack:**
- `.specify/memory/constitution.md` (v1.1.0, 85 lines) — "single source of truth above all agent files": context detection (Ralph loop vs interactive chat), principles (Native First; Test-Driven Implementation; Simplicity & YAGNI; Safety & Reliability — email/SMS/billing disabled by default), autonomy config (YOLO disabled; Git commit autonomy enabled), and the current validation policy (2026-09-13): no CI, everything local, evidence recorded per revision.
- **AGENTS.md** (188 lines) — universal baseline consumed by Codex CLI, Cursor, Aider, Jules, OpenHands, Sourcegraph Amp, Factory; CLAUDE.md cross-references it for Claude Code; `.github/copilot-instructions.md` restates for Copilot. House style: imperative voice; every rule *verifiable* ("Filter every query by org_id," not "Be careful with multi-tenancy"); runnable commands over prose; ~200-line cap; markdown only. Includes safety rules (never commit secrets; no destructive ops without explicit per-action authorization; stop and ask when unsure), a validation checklist (black/ruff/mypy/tests/secrets-grep/migration-exists), PR rules, and a 5-level instruction hierarchy (user request > repo rules > path-scoped Copilot rules > strategy doc > inferred best practice; "follow the more specific and safer one").
- **Anti-hallucination rules:** don't invent paths/functions/commands — grep first; read schema/config facts from canonical source, not memory; when ambiguous, present 2-3 differentiated options; research tasks carry a hard-stop checklist (≥3 angles, sources read in full, limitations included).
- **Rule graduation pipeline:** `docs/source-repos.md` tracks external sources (pending → extracted → promoted); `docs/research-log.md` records dated observations *separate from promoted rules*; stable observations must be tested on a real change before promotion into AGENTS.md/CLAUDE.md, then upstreamed to `tomqwu/GenAI_Common`. "Observations never become silent rules."
- **Local code review** (docs/ai-pr-review.md): review the complete diff locally; check correctness, security, org isolation, authorization, migrations, negative-path coverage; record findings with severity and file/line refs and the reviewed head/base SHAs in the PR; invalidate stale evidence after changes; "Missing review is not approval"; reviewer agents must not merge. It explicitly supersedes a retired Ollama PR-review gate ("Ollama is not a code-review provider").
- **Evidence discipline:** run `make test-all` per PR; record commands, pass/skip/failure counts, date, environment, limitations, pushed head SHA; "Do not hide flakes or treat skipped tests as passed"; "GitHub does not independently attest local runs; never fabricate a successful status check." PR/commit bodies use a fixed Summary/Changed files/Validation/Follow-ups format. `docs/playbooks/validation.md` models the standard: it records initial failures ("this initial failure is not omitted from the evidence") and records mypy debt honestly ("835 errors in 40 files; not a pass").

## 3. Testing Philosophy

**Seven Python tiers** (docs/TESTING.md), each run in a separate process by `make test-all`: (1) Unit `tests/unit/` — fast, mocked auth via conftest.py; (2) API `tests/api/` + `tests/security/` — real HTTP + real JWT against isolated SQLite; (3) CLI `tests/cli/` — subprocess YAML→JSON; (4) Integration `tests/integration/` — real DB; (5) Web `tests/web/` — in-process cookie/HTMX; (6) Contract `tests/contract/` — OpenAPI snapshot compatibility; (7) Browser `tests/e2e/` — Playwright against a disposable live app. Plus `make test-mobile` (Flutter). Dated full-suite evidence: **1,464 passed / 21 skipped**.

**TDD everywhere:** write the failing test first, implement, `make test-unit`; the tasks template requires tests to fail before implementation. Right-tier discipline: an explicit anti-pattern is "Mocking the database in integration tests." Negative-path assertions required for every new feature. Fast loop: `make test-unit-fast` skips slow bcrypt tests (~7s). Unit tier auto-mocks auth; `@pytest.mark.no_mock_auth` opts out; API tier runs real-JWT tenancy regressions.

**Playbook-based acceptance:** two six-week domain scenarios — church (CH-01..CH-08) and basketball (BB-01..BB-08) — plus shared journeys BO-01..BO-12 (baseline roster, availability self-service, recurrence scope, rolling week-7 horizon, owned local mail capture, personal calendar, account recovery, two-tenant isolation, late cover, qualification changes, schedule changes) and domain drills CH-D01..03 / BB-D01..03. `church.md` is genuinely operational: an actors/access table, a weekly operating rhythm, and disruption drills with acceptance criteria (e.g., CH-04: block both worship leaders → publication rejected, prior roster stays live). Executable fixtures `church.json`/`basketball.json` declare roles, headcounts (14 baseline members + a qualified replacement), critical role, late-cover roles; a pytest plugin discovers them, parameterizes stable scenario IDs, supports `--playbook`/`--playbook-dir`, and an external `food-bank.json` example. Browser variants run at 360px and 1440px and verify an 84-slot horizon (12 events × 7 roles) with an *independent oracle* (exact role counts, distinct qualified assignees, non-overlap, balanced loads within one).

**Coverage manifest:** `docs/playbooks/coverage.json` binds every BO/CH/BB scenario, actors, preconditions, operations, expected results, execution tiers, evidence paths, and honest status (automated/partial/manual/blocked — blocked "includes the manual tier so it cannot look automated"). Pytest validates it *before* collecting playbook cases, so removing a required role or scenario fails collection.

**Why no CI:** an explicit owner policy (ROADMAP.md 2026-09-14: "The owner directs: no CI checks; everything is validated locally"), restated in constitution, TESTING.md, README, AGENTS.md. GitHub hosts source/issues/PRs/Pages only. All checks run locally, recorded in the PR against head/base SHAs. There are even policy-regression tests (`tests/unit/test_local_validation_policy.py`). The philosophy in one line: "Local results are procedural evidence, not independently attested by GitHub." Old CI proposals were reclassified with historical banners, not deleted.

## 4. Multi-Tenant Security Patterns Worth Teaching

- **org_id filtering as P0:** "Every database query MUST filter by org_id… A missing org_id filter is a cross-tenant data leak. Treat it as a P0 bug" (AGENTS.md). Enforced via `verify_org_member(person, org_id)` in `api/dependencies.py`; routes use `Depends(get_current_user)`/`get_current_admin_user)`; "Never read user state from the request body."
- **Permission roles vs qualifications:** exactly one permission role per account (`volunteer` or `admin`); scheduling qualifications (usher, worship_leader, coach, center) live in the same JSON roles array but are never interpreted as permissions; normalized via `api.roles.normalize_roles`. church.md: "Do not grant admin access merely because someone leads a ministry."
- **Atomic bootstrap + invitation-only growth:** `/auth/signup` atomically creates org + first admin and rejects existing org IDs; no public join; later members only via admin-created token invitations.
- **Executable authorization matrix:** `api/route_auth_policy.py` classifies every mounted operation as public/public-token/public-callback/member/admin; `tests/unit/test_api_route_auth_policy.py` compares it to the live route table and fails on missing/stale/miswired routes. `docs/API_AUTHORIZATION.md` gives a 6-step change protocol.
- **Tenant-bound credentials:** every access token and browser session carries person `sub` + `org_id`; auth reloads an active person by both; missing/mismatched tenant claim, inactive membership, or deleted person invalidates the credential; password changes/resets revoke older credentials.
- **Deliberate status semantics:** invalid bearer → 401; missing bearer on protected route → 403; authenticated actor naming a foreign org → 403; guessed resource ID → looked up inside the actor's tenant → 404 (no existence leak).
- **Two-tenant acceptance as a feature (BO-12):** Church and Basketball coexist in one disposable server; each admin sees only its own directory; every qualification signs in as a volunteer at both widths and is denied admin surface, invitations, publication, foreign-person reads, peer availability writes.

## 5. Solver Case Study: Classic Algorithm + AI-Assisted Development

`api/core/solver/heuristics.py` (357 lines) implements `GreedyHeuristicSolver`, strategy "feasible_first": sort events by start; per required role, filter candidates by qualification, overlap, vacation/RRULE-blocked dates, and person-scoped hard constraints; score the rest by penalty = Σ soft-constraint penalties + 10 × current assignment count (**fairness**) − change-min bonus (default weight 100) if the (event, person) pair was in the prior published solution; pick lowest; verify role coverage and emit hard violations ("Role musician needs 2, got 1"). Metrics: **health score** = 0 with any hard violation, else max(0, 100 − soft_score/10); **fairness** = stdev of per-person counts.

The constraints DSL (`api/core/constraints/`: dsl.py 38, eval.py 153, predicates.py 101, persisted.py 149 lines) separates binding (key/scope/applies_to/severity/predicate+params) from evaluation. REST supports exactly three saved rules (docs/SCHEDULING_CONSTRAINTS.md): `max_assignments` (hard), `min_gap_hours` (hard), `cooldown` (soft, weighted); periods `P1M`/`P{N}D`; invalid input → 422, never a silent no-op; availability, time-off, distinct-people-per-slot, and no-overlap are built-in invariants. The doc fences the DSL: "The REST mapper is not an arbitrary expression language."

Why it teaches: (a) the entire algorithm fits in one sitting; (b) AI-assisted evolution is traceable — `specs/020-solver-quality-changemin/spec.md` drove change-minimization, and heuristics.py carries a comment pointing at that spec; (c) the playbook oracle continuously validates it; (d) validation.md shows acceptance catching real bugs (assignments omitted the selected role; a multi-skilled person could conceal an unfilled role; overlapping events were schedulable — each reproduced then repaired); (e) honest limits: "attendance, ministry suitability… remain human responsibilities, not inferred from a green solver score."

## 6. Teachable Takeaways (lesson → anchor files)

1. **Write an AGENTS.md that actually constrains agents** — imperative, verifiable, runnable, <200 lines. Anchors: `AGENTS.md`, `docs/ai-agent-coding-strategy.md`.
2. **Layer agent instructions, don't duplicate** — constitution > AGENTS baseline > CLAUDE addenda > Copilot restatement, with explicit precedence. Anchors: `.specify/memory/constitution.md`, `CLAUDE.md`, `AGENTS.md`.
3. **Run a full spec-kit workflow** — specify → clarify → plan → checklist → tasks → analyze → implement with the spec/research/data-model/plan/contracts/quickstart/checklists/tasks artifact set. Anchors: `.specify/templates/*`, `specs/014-security-hardening/*`, `docs/SPEC_KIT_SETUP.md`.
4. **Gate planning with a Constitution Check** — pass/fail gate re-checked after design; violations require a complexity-justification table. Anchor: `specs/014-security-hardening/plan.md`.
5. **Make research a first-class artifact with a graduation pipeline** — observations separate from promoted rules; source status tracking. Anchors: `docs/research-log.md`, `docs/source-repos.md`.
6. **Evidence discipline** — record commands, counts, SHAs; never fabricate checks; include failures. Anchors: `docs/ai-pr-review.md`, `docs/playbooks/validation.md`, `docs/TESTING.md`.
7. **Build an executable coverage manifest** — pytest-validated coverage.json with honest statuses. Anchors: `docs/playbooks/README.md`, `coverage.json`.
8. **Playbook-based acceptance** — six-week operational scenarios as JSON fixtures parameterized through API and browser tiers at two viewport widths with an independent oracle. Anchors: `docs/playbooks/church.md`, `church.json`, `tests/playbooks/examples/food-bank.json`.
9. **Make authorization executable** — route policy file + drift-failing test. Anchors: `docs/API_AUTHORIZATION.md`, `api/route_auth_policy.py`, `tests/unit/test_api_route_auth_policy.py`.
10. **org_id filtering as a P0 cultural rule** — plus permission/qualification separation and tenant-bound tokens. Anchors: `AGENTS.md`, `api/dependencies.py`, `CLAUDE.md`.
11. **Classic algorithm, AI-assisted process** — read the whole solver, trace one feature (change-min) from spec → code comment → oracle. Anchors: `api/core/solver/heuristics.py`, `api/core/constraints/`, `docs/SCHEDULING_CONSTRAINTS.md`, `specs/020-solver-quality-changemin/spec.md`.
12. **Honest documentation hygiene** — historical banners, INDEX separating current entry points from a historical catalog, explicit "not verified" statements. Anchors: `docs/INDEX.md`, `docs/TEST_STRATEGY.md`, `docs/ROADMAP.md`.

Bonus micro-lesson: **verify generated artifacts** — `specs/000-user-onboarding/tasks.md` still references a renumbered spec path, and the 014 checklist's priority counts don't match the spec's six P1 stories — living governance docs drift, exactly what AGENTS.md's "search for stale commands, counts, check names" rule targets.
