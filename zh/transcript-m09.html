第 1 部分

AI Product Studio · 模块 9 / 10 · 未录制

欢迎来到第 9 模块：用 GitHub Pages 发布产品目录。本模块免费，也没有任何前置要求。如果你从没打开过终端，就从这里开始。学完本模块，你会拥有：已经装好并验证过的工具，一个你亲手克隆、修改并推送的仓库，以及一个放在你自己的 GitHub Pages 地址上的公开产品目录。每条命令都给两遍，一遍用于 Windows，一遍用于 macOS，并排列出，你永远不需要自己去换算。

第 2 部分 — 学完本模块，你能够……

M9 · 用 GitHub Pages 发布产品目录 · 未录制

下面是你将能做到的五件事。安装 Git 和 GitHub CLI，并用脚本而不是猜测来证明环境已经配好。在终端里浏览你的文件夹。克隆一个仓库，修改它，再把改动推送回去。用 GitHub Pages 发布一个静态网站。还有，说清楚 Pages 允许什么、禁止什么，因为最后这一条决定了你的产品目录的整体设计。实验会检查全部五项，测验也一样。

第 3 部分 — M9.1 — 四样东西，各管一件事

M9.1 · 未录制

四个名字，各管一件事。终端是一个窗口，你在里面输入命令，而不是用鼠标点击。Git 记录一个文件夹的各个版本，每个保存下来的版本叫作一次提交。GitHub 是一个网站，它保存那个文件夹的一份副本，这份副本叫作仓库，GitHub 还能把它发布成网站。还有 gh，也就是 GitHub CLI，让你在终端里操作 GitHub，而不必在网站上一路点击。Git 在你的电脑上。GitHub 在互联网上。命令行工具把两者连接起来。

第 4 部分 — 打开终端

M9 · 用 GitHub Pages 发布产品目录 · 未录制

现在就打开一个终端。在 Windows 上，按 Windows 键，输入 terminal，然后按 Enter。在 Mac 上，按 Command 加空格，输入 terminal，然后按 Enter。你会看到一行字，末尾是你的文件夹名和一个符号。这一行就是提示符，它只是在等你输入。本模块里的所有内容都在提示符后面输入，然后按 Enter 运行。这里的 Windows 命令都是写给 PowerShell 的，也就是 Windows Terminal 默认打开的环境。

第 5 部分 — 每样工具一条命令安装

M9 · 用 GitHub Pages 发布产品目录 · 未录制

每个系统都有一个包管理器，用一条命令就能安装软件。在 Windows 上是 winget，它随微软的 App Installer 一起提供。在 Mac 上是 Homebrew，用 Homebrew 官方说明里的一行命令安装。之后，Git 和 GitHub CLI 各只需要一条命令。有两个坑。在 Mac 上，Homebrew 结束时会打印几行设置命令；一定要运行它们，否则会找不到 brew。在 Windows 上，已经打开的终端看不到新装的命令，所以要关掉它，打开一个新窗口，而不只是新标签页。

第 6 部分 — 告诉 Git 你是谁，然后登录

M9 · 用 GitHub Pages 发布产品目录 · 未录制

每次提交都会记录一个名字和一个邮箱，所以把你的名字和邮箱告诉 Git 一次，这台电脑上的每个仓库就都会用它。用你 GitHub 账号的邮箱；如果你不想公开自己的邮箱，也可以用 GitHub 提供的私密 noreply 地址。然后用 gh auth login 登录。它会问四个问题：选择 GitHub.com，然后选 HTTPS，然后对用你的 GitHub 凭据来认证 Git 选 yes，最后选用网页浏览器登录。它会显示一个一次性验证码，打开你的浏览器，你把验证码粘贴进去。之后，Git 推送时就不会再要你输入密码。

第 7 部分 — 证明：靠脚本，不靠感觉

M9 · 用 GitHub Pages 发布产品目录 · 未录制

这是环境检查脚本，在 PowerShell 下真实运行的结果。它检查四件事：Git、GitHub CLI、你的名字和邮箱，以及你是否已经登录。每一项都会打印 pass 或 fail，每个 fail 都会打印能修复它的确切命令。这台机器缺少 CLI，也没有登录，脚本如实说了出来，修复方法就写在下面。规则很简单。修好第一个 fail，打开一个新的终端窗口，再运行一次，直到它显示 4 of 4。一个能证明你的环境已就绪的脚本，胜过一种大概已经弄完了的感觉。

第 8 部分 — 行动步骤 — M9.1

M9 · 用 GitHub Pages 发布产品目录 · 未录制

你的第一个行动步骤。运行环境检查，直到它显示 4 of 4，然后把完整输出粘贴到一个名为 evidence.md 的新文件里。在本模块剩下的部分，你会一直往这个文件里添加内容。保留你一路上遇到的每一次失败，连同修好它的那一行命令。这份记录比一次干净的运行更有价值，因为它正是下一个人需要的东西。

第 9 部分 — M9.2 — 你总是身处某个位置

M9.2 · 未录制

终端总有一个当前文件夹，就像文件窗口总是显示某一个文件夹一样。终端刚打开时，这个文件夹就是你的主目录。五条命令几乎能覆盖一切，而且在 Windows 和 Mac 上完全一样。pwd 显示你在哪里。ls 列出这里有什么。cd 后面跟一个名字，就进入那个文件夹。cd 点点，回到上一级。还有 cd 波浪号，无论在哪里都能直接回到主目录。想在普通窗口里看到这个文件夹，在 Windows 上输入 start 点，在 Mac 上输入 open 点。再按 Tab 键，让它帮你补全长名字。

第 10 部分 — 路径：绝对、相对，以及斜杠

M9 · 用 GitHub Pages 发布产品目录 · 未录制

从磁盘顶层开始的路径是绝对路径。从你当前位置开始的路径是相对路径。Windows 用反斜杠分隔文件夹，macOS 用正斜杠，但 PowerShell 也接受正斜杠，所以像 code/my-catalog 这样的路径在两个系统上都能用。有一个坑比其他任何坑都更浪费初学者的时间：文件夹名里带空格。要么用引号把名字括起来，要么更好的做法是：项目名里永远不用空格。改用连字符。

第 11 部分 — 克隆：一份副本，连同历史

M9 · 用 GitHub Pages 发布产品目录 · 未录制

克隆就是把一个仓库复制到你的电脑上，连同它的全部历史。有两种方式，效果相同。gh repo clone 接受简短的所有者和名称，并使用你刚才设置好的登录。git clone 接受完整地址，也就是你在任何仓库的绿色 Code 按钮上看到的那个地址。无论用哪一条，都会在你此刻所在的文件夹里，新建一个以仓库命名的文件夹。这是初学者最常犯的错误：在主目录里克隆，然后却去 code 文件夹里找。先确认你在哪里。

第 12 部分 — 把改动送回去的循环

M9 · 用 GitHub Pages 发布产品目录 · 未录制

一旦一个文件夹成了仓库，每次改动都要经过同样的四条命令送回去，而且总是按这个顺序。git status 显示自上次提交以来改了什么。git add 点，会把这个文件夹里的每一处改动都选入下一次提交，它什么都不打印，这就表示成功。git commit 把这些改动保存为一个版本，并附上一条说明改了什么的信息。还有 git push，把你的新提交发送到 GitHub。每一次都要在前后各看一遍 git status。之后，一个干净的工作区就说明一切都送上去了。

第 13 部分 — 证明：真实运行一遍这个循环

M9 · 用 GitHub Pages 发布产品目录 · 未录制

这就是那个循环，在产品目录起始项目上真实运行的结果。提交之前，git status 列出了五个新文件。这次提交把六个文件保存为一个版本，并给出一个短编号。push 的最后一行写着 main 箭头 main，意思是 GitHub 现在已经有了它。最后的 status 显示 nothing to commit, working tree clean。你的短编号会不一样，但形状会完全一样。最后那一行就是改动已经送达的证明。

第 14 部分 — 行动步骤 — M9.2

M9 · 用 GitHub Pages 发布产品目录 · 未录制

你的第二个行动步骤。进入你的 code 文件夹，用任意一条命令克隆本课程，进入新文件夹，列出里面有什么。然后回到上一级，打印你所在的位置，以此证明。把两段输出都粘贴到你的证据文件里。现在你已经知道怎样在终端里找到电脑上的任何东西了。

第 15 部分 — M9.3 — 五个文件，你只改一个

M9.3 · 未录制

产品目录起始项目有五个文件，你只改其中一个。products.js 保存你的店名、你的联系链接，以及你的产品列表。页面本身是 index.html，你在里面改一行描述。颜色写在样式表里。应用脚本负责绘制卡片、分类按钮、搜索和排序，你永远不需要碰它。还有一个名字很奇怪的空文件，你要保留它。它告诉 GitHub Pages 按原样发布你的文件。

第 16 部分 — 为什么数据是脚本，而不是 JSON

M9 · 用 GitHub Pages 发布产品目录 · 未录制

每个产品是一个小块：一个 id、一个名称、一个分类、一个写成纯数字的价格，以及一句话简介。如果有图片，就加上图片；如果你在别处运营结账页面，就加上购买链接。为什么这是一个脚本，而不是一个数据文件？因为浏览器不允许从你磁盘上打开的页面读取单独的数据文件，但会运行脚本。所以你双击就能预览产品目录，不需要服务器，而你看到的正是全世界将会看到的。

第 17 部分 — 同样的模式，更大的网站

M9 · 用 GitHub Pages 发布产品目录 · 未录制

这不是玩具模式。AI × QE 是本课程中的专业领域案例研究，它本身就是一个 GitHub Pages 网站。它把四张简报卡片放在一个数据文件里，由一个模板遍历这个文件来绘制它们。你的产品目录把产品放在一个数据文件里，由一个脚本来绘制它们。区别在于各自的发布方式。你的产品目录按原样发布一个分支。AI × QE 运行一个工作流，它先构建网站、运行自己的检查，然后才部署。同一个托管平台，两种模式，而且一个网站可以从一种模式成长到另一种。

第 18 部分 — 从分支发布

M9 · 用 GitHub Pages 发布产品目录 · 未录制

发布只需要点四下，而且只做一次。在你的仓库里，打开 Settings，然后打开 Pages。在 Build and deployment 下，把 Source 设为 Deploy from a branch。选择 main 分支和根文件夹，然后保存。然后等待。GitHub 说，一次改动最多可能需要十分钟才会出现，Actions 标签页会在这期间显示这次运行。你的地址是你的用户名，加上 .github.io，再加上斜杠和你的仓库名。此后，每次推送都会自动重新发布网站。你永远不需要重复这些步骤。

第 19 部分 — 限制，来自 GitHub 自己的页面

M9 · 用 GitHub Pages 发布产品目录 · 未录制

GitHub 公布了这些限制，对一个产品目录来说相当宽裕。一个已发布的网站最大可以到 1 GB。带宽有每月 100 GB 的软限制，构建有每小时 10 次的软限制。单次部署超过十分钟就会超时。在免费账号上，公开仓库可以免费使用 Pages；从私有仓库发布则需要付费计划。让每张照片保持小巧，你就永远不会接近这些限制中的任何一项。

第 20 部分 — 是产品目录，不是网店

M9 · 用 GitHub Pages 发布产品目录 · 未录制

有一条规则决定了整体设计，它出自同一个 GitHub 页面。Pages 不允许被用作免费托管，来经营线上业务或电子商务网站，或任何以收款为主要目的的网站。一个介绍你的产品的目录没问题。一个网店则不行。这就是起始项目没有购物车、也没有结账功能的原因。每个产品都可以链接到一个在专为收款而建的地方运行的结账页面；如果没有，按钮就只显示 Ask about this，并打开一封邮件。

第 21 部分 — 行动步骤 — M9.3

M9 · 用 GitHub Pages 发布产品目录 · 未录制

你的第三个行动步骤。把六个示例产品换成至少三个你自己的产品，可以是真实的产品，也可以是你在本课程中正在构建的产品。双击预览这个页面。然后在你的证据文件里写一行，说明每个产品的按钮将指向哪里：一个你在别处运营的结账页面，或者暂时用 Ask about this。

第 22 部分 — 实验 M9 — 发布你的产品目录

实验 M9 · 未录制

这个实验带你从什么都没装走到一个上线的产品目录，共八个步骤，用时六十到九十分钟，大部分时间是在等待安装。你创建一个账号，并证明你的环境已经配好。你创建一个 code 文件夹，并克隆本课程。你创建自己的公开仓库，名为 my-catalog，把起始项目复制进去，再把它改成你自己的。你提交并推送。然后你发布它，在手机上打开地址，修改一个价格，看着它重新发布。每一步都会告诉你要往证据文件里粘贴什么。

第 23 部分 — 测验 M9 — 考查什么

M9 · 用 GitHub Pages 发布产品目录 · 未录制

这个知识检查有八道题。它会问：为什么在 Windows 上安装之后需要一个新的终端窗口；缺少名字和邮箱实际会阻止你做什么；克隆会落在哪里，以及为什么；push 做了哪些 commit 不做的事；以及为什么你的产品目录要链接到外部的结账页面，而不是直接收款。两道简答题都很实用：修好一位同学坏掉的环境，以及在当天发布一位店主的产品。

第 24 部分 — 回顾

M9 · 用 GitHub Pages 发布产品目录 · 未录制

回顾一下。用 winget 或 Homebrew 安装你的工具，再用环境检查证明它们，直到它显示 4 of 4。用显示当前目录、列出内容、切换目录、返回上一级和新建目录这几条命令四处移动。用 status、add、commit 和 push 把每一次改动送回去。从 main 分支发布一次，之后每次推送都会重新发布。还要记住这条边界：GitHub Pages 展示你的产品，而别处的结账页面负责把它们卖出去。

第 25 部分 — 讨论题

M9 · 用 GitHub Pages 发布产品目录 · 未录制

离开之前，贴出你的产品目录地址，以及你花时间最长的那一个配置步骤，附上修好它的那一行命令。然后在手机上打开一位同学的产品目录，告诉他们你点的第一个没有按你预期工作的东西。这一句话会是他们的页面这周得到的最有用的反馈。
