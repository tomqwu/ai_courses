三个机械化的执行机制

  • 身份只来自凭证。
  • 「永远不要从请求体读取用户状态。」

枚举止于 404

  • 目标先通过操作者的组织加载。
  • 他人的资源与不存在的资源看起来完全一样。
  • 统一返回 403 反而会确认资源存在。

来源SignUpFlow/api/dependencies.py:61-66

枚举靠一种查询形态就能终结，这条查询现在就在幻灯片上：get_person_in_actor_org 在 WHERE 子句里同时带上 id 和操作者的组织来加载目标行，匹配不到就抛出 404。 所以一个他人的人员和一个不存在的人员得到同样的回答：查无此项。 这很重要，因为 403 等于在说「存在，但不是你的」，一个拥有完全合法账号的攻击者就可以遍历你的 id 空间，摸清你有哪些资源存在。 看这段代码：过滤同时带着两个条件，查不到就抛出异常，函数里再没有别的地方会泄露资源是否存在。

M5.2 两套词汇，一个数组

6 个部分

  • 同一个 roles 数组——但含义从不相通。
  • 资格从不授予管理员权力。

来源SignUpFlow/api/roles.py:8 · docs/playbooks/church.md:26

SignUpFlow 中的一个人员带有一个 roles 数组，里面放着两种毫不相干的字符串。 权限角色描述一个账号可以做什么，共有两个：admin 和 volunteer。 资格描述一个人能做什么，比如引座员、教练和敬拜带领，求解器用它们来填补角色空位。 它们共用这个数组，但从不共享含义。 陷阱来自自然语言：她带领敬拜，所以应该给她打开管理员开关。 教会运营手册用一句话拒绝了这种想法：不要仅仅因为某人带领一个事工就授予管理员权限；它的操作者表把敬拜协调人列为 volunteer 加敬拜带领资格，而不是 admin。

漂移的输入会大声失败

  • 精确匹配 → 权限角色；其余一律 → 资格。

来源SignUpFlow/api/roles.py:38-53

这条策略不是散文，而是可执行的，现在它就在幻灯片上。 在 roles.py 中，normalize_roles 接收管理员提交的数组，并让账号访问权限变得明确，正如它的文档字符串所说。 与权限角色集合精确匹配的是权限角色，其余一律当作资格处理。 但漂移的情况会大声失败，两种拒绝在代码中都看得到。 像大写 ADMIN 这样经大小写折叠后发生冲突的值会抛出异常：它是一个有歧义的权限角色。 如果数组里带了两个权限角色，函数会抛出异常，消息是：请只选择一个账号访问角色。 正是这些拒绝让这套词汇变得安全：漂移永远不会悄无声息地变成权限。

总结

2 个部分

回顾

  • M5.1 — P0 规则 + 三个执行机制 + 以 404 防枚举。
  • M5.2 — 一个权限角色；资格从不赋予权力。
  • M5.2 — 策略字典可执行；测试抓住漂移。
  • M5.3 — 七个层级在独立进程中运行；带日期的证据会退役。
  • M5.3 — 运营手册测试拒绝；判定器是独立的。
  • M5.3 — 清单状态相互耦合；校验先于收集。

六行、三个分段、一条主线。 在 M5.1 中，规则写在每个智能体都会读的基线里，三个机制强制执行它，猜测的 id 返回 404，于是枚举失效。 在 M5.2 中，恰好一个权限角色，资格共用数组但从不赋予权力，授权矩阵是一个由测试与实时应用比对的字典。 在 M5.3 中，七个层级各自证明不同的东西，运营手册的验收标准关乎拒绝，判定器从排班表重新计算，清单在收集之前就被校验。 主线是：智能体以机器的速度生成查询，所以防护也必须是机械化的。
